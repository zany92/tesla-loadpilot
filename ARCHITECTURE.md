## D1 — Product form: ONE repo, HACS integration + referenced ESPHome packages

**Decision: option (c) carrying a full option-(a) integration** — a single
repository that HACS distributes as a *custom integration*
(`custom_components/loadpilot/`), with the generic firmware living in the
same repo under `esphome/packages/` and consumed by users through ESPHome
**remote packages pinned to the same release tag**:

```yaml
# user's charger-node yaml (their ESPHome dashboard)
packages:
  loadpilot:
    url: https://github.com/<owner>/tesla-loadpilot
    files:
      - esphome/packages/twc-core.yaml
      - esphome/packages/boards/kc868-a6.yaml
    ref: v0.1.0          # ALWAYS a tag, never main
```

Why:

- **HACS cannot flash ESP32s and does not distribute ESPHome YAML.** Any
  form of the product therefore has two delivery channels no matter what;
  putting both in one repo gives them one version number, one changelog,
  one issue tracker, and lets the integration verify firmware/version skew
  at runtime (see D4).
- **(b) blueprints is rejected as the backbone**: the HA-side value is a
  config flow (phases, contract limit, buffer, meter mapping, mirror
  entities), derived sensors, services, diagnostics and Repairs — none of
  which blueprints can model. Blueprints remain possible later as optional
  add-ons for the orchestration layer (vehicle-first policy), not as the
  product's spine.
- **The integration is not a hard dependency of regulation** (see D2). It
  is the installer/observer/orchestrator. A user can run firmware-only;
  the integration is what makes the product installable, observable and
  supportable at HACS quality.

## D2 — ESP/HA boundary: the law never needs HA

Hard rule, restated from the measured control law (`docs/40_LOI_DE_COMMANDE.md`
§6–§10): **everything that keeps the charger regulated and the contract safe
lives in firmware and keeps working with Home Assistant down, the cloud
down, or both.**

| Layer | Owns (non-negotiable) | Never does |
|---|---|---|
| **Charger node firmware** (`twc-core.yaml`) | Worst-phase **symmetric clamped publication** (`avail_p = clamp(limit×(1−buffer)−bias−measure_p, 0, L)`; `pub = L − min(avail)`); **escalation** 120 s at zero-avail → publish `L+0.1` (clean stop); **fail-safe** (publish `main_breaker` ⇒ margin 0 ⇒ charge blocked) at boot and whenever no source is healthy; **source priority** UDP > HA mirror > fail-safe; bias target+ramp (+immediate apply when contactor open); Modbus server < 66 ms response; 1:1 plausibility by construction (no smoothing, no vehicle estimator, no internal state beyond the escalation timer) | Depend on HA, cloud, or the integration for any of the above |
| **Meter provider firmware** | Acquire + broadcast the 6 quantities (UDP contract below) at ~1 Hz, encrypted; **go silent on sensor failure** (never freeze-and-repeat) | Smooth, average, or estimate |
| **HA integration** (`loadpilot`) | Config flow (writes the node-resident knobs), derived sensors (headroom/phase, worst phase, regulation state), services, HA-mirror wiring (backup measure path), diagnostics, Repairs (version skew, stale sources), optional orchestration policy (vehicle-first, notifications) | Sit in the real-time loop; hold any parameter the firmware needs to boot safe |

**Runtime knobs are node-resident**: `contract_limit_a`, `buffer_pct`, bias
target, `control_enabled` are ESPHome `number`/`switch` entities on the
charger node with safe defaults and flash restore. The integration *writes*
them (config flow + options), it never *hosts* them. HA reboot ⇒ nothing
changes at the wallbox.

Failure matrix (design intent, to be QA'd as such):

| UDP | HA | Result |
|---|---|---|
| fresh | any | regulation continues (validated in prod 17/08) |
| stale > 5 s | up | HA mirror takes over (degraded latency, documented) |
| stale | down | fail-safe: charge blocked (behaves like a dead meter) |
| node down | — | TWC native behaviour without meter (charger's own protection); documented, out of our loop |

## D3 — Generality: three abstractions, France first

1. **MeterProvider** — anything that ships the 6 quantities
   (`lky_ia/ib/ic` in A, `lky_pa/pb/pc` in VA, import-positive, raw) over
   the encrypted UDP contract (port 18511, XXTEA + rolling code, 1 Hz
   heartbeat + immediate deltas). Contract spec: `docs/15_FOURNISSEURS_MESURE.md`
   §1. Eligibility gate is **cadence ~1 Hz per-phase**. Implementations:
   `teleinfo-fr.yaml` (proven in production), then `dsmr-p1.yaml`
   (NL/BE), `sml-de.yaml` (DE/AT, honest caveats), `ct-clamps.yaml`
   (universal fallback). Country quirks (Tempo, STGE overload bit) stay
   **inside the provider** and surface only through one optional generic
   signal: `meter_overload` (binary).
2. **ChargerBackend** — TWC Gen 3 via Neurio/Generac Modbus emulation is
   the only implementation and the near-term scope. The backend boundary is
   exactly "consumes the 6 quantities + a limit, exposes published values":
   `twc-core.yaml` (logic) + `boards/<board>.yaml` (pins/transceiver/
   network only — KC868-A6 validated, ESP32-S3 core drafted, A4/A8/A16
   pending per `docs/20_FIRMWARE.md` §2.9). A future charger type is a new
   core package, not a fork of this one.
3. **Phase topology** — `phases: 1 | 3` in the config flow and as firmware
   substitution. Mono publishes phases B/C at 0; the worst-phase law
   degenerates correctly (min over one phase).

## D4 — Versioning & compatibility

- **SemVer, one version for the whole repo**, tagged `vX.Y.Z`. The tag is
  what HACS installs *and* what ESPHome `ref:` pins — integration and
  firmware are released in lockstep, always.
- `0.x` until (a) the PVi1 attribution agreement is settled and (b) at
  least one non-reference installation validates. Breaking changes to the
  UDP contract or the entity contract bump MINOR during 0.x, MAJOR after.
- **Skew detection**: `twc-core.yaml` exposes
  `sensor.loadpilot_twc_fw_version` (text, = package version). The
  integration compares it to its own version and raises a **Repair issue**
  on mismatch (never blocks regulation).
- Compatibility floors (declared, enforced where possible):

| Component | Minimum | Why |
|---|---|---|
| Home Assistant | 2025.12 (`hacs.json`) | current config-entry & Repairs APIs; matches HACS expectations |
| ESPHome (both nodes) | 2025.2 | `udp` + `packet_transport` with XXTEA encryption & rolling code |
| TWC Gen 3 firmware | 26.18 (calibration reference) | the entire measured law (`docs/40_LOI_DE_COMMANDE.md`); re-calibrate on TWC firmware change — stated prominently in docs |
| Boards | KC868-A6 (validated) | others per matrix `docs/20_FIRMWARE.md` §2.9 |

## Non-goals (v0.x)

- No solar/export management (reference install is import-only, GRID mode).
- No vehicle cloud API in the shipped product (Fleet/BLE orchestration is
  documented as a pattern in `docs/`, Loupiac-specific implementation is
  not published).
- No YAML-only install path for the integration (config flow only).
- No Tesla imagery, ever; no LICENSE file until the PVi1 agreement lands
  (placeholder documents the intent).
